The 60-second version

If you only read one page, read this one.

A loop asks: should this one agent keep going?

A graph asks: who runs next, with what state, under which rules?
Who this is for. You already build with a coding agent that runs tools in a loop until the tests pass. This guide shows what changes when one loop stops being enough, and how to tell when that has happened.
  1. Loops are not dead. A loop is the smallest possible graph, and the nodes of a graph run loops inside them. Same system, different zoom level.
  2. The thing you design changes. Less prompt, more topology: nodes that do work, edges that decide what runs next, shared state, and contracts.
  3. Graphs pay off when you know something about the shape of the work: steps that can run in parallel, checks that must be independent, gates that must never be skipped, progress that must survive a crash.
  4. They are not free. Anthropic's multi-agent research system scored 90.2% higher than its single agent on an internal evaluation, and used about 15 times the tokens of a normal chat.
  5. Start with one good loop. Add graph structure only when your traces show the loop hiding parallel work, self-grading, or fragile state.

Part 1 · From loops to graphs

Where a single loop runs out of road.

Feng et al. (August 2026) name three structural walls. More turns and a bigger model do not remove them.

Wall 1

Everything happens in a line

Log analysis, bug reproduction and code inspection could run side by side. A single loop does them one after another. Latency multiplies, and an early mistake flows quietly downstream.

Wall 2

It grades its own homework

Giving one loop several personas does not help. Writing and critiquing in the same context window means the agent shares blind spots with itself and mistakes confidence for evidence.

Wall 3

A transcript is not a database

State lives in the chat history. A small error early in a long run cannot be isolated or undone without throwing away the whole run.

Symptoms you have probably seen
The “Ralph loop”Re-prompt against the goal until it stumbles into a pass or hits the step limit.
Context bloatEvery call re-reads the full history, including stale errors and failed attempts. Cost and latency climb as the run gets longer.
Going in circlesIn the original ReAct error analysis, 47% of failures were the agent repeating the same thought and action; another 23% came from empty search results it could not recover from.

Three debts a fast loop quietly runs up.

Addy Osmani's warning to anyone running autonomous coding loops at scale.

1

Intent debt

Whenever project context is not written down, the loop does not stop and ask. It fills the gap with a confident guess, and guesses differently on the next cycle.

The tellThe same architectural decision gets re-made, differently, every run.
Pay it downWrite the conventions, build steps and verification rules into files the agent always reads, such as SKILL.md.
2

Comprehension debt

The loop generates and ships code faster than people can read the diffs. The codebase grows while the team's mental model falls behind.

The tellNobody can explain how a merged feature works without asking the agent.
Pay it downKeep external state that humans read too: trackers, decision notes, milestones that persist across runs.
3

Cognitive surrender

Green test suites lull engineers into approving whatever clears the checks. Independent judgement about quality and architecture stops forming.

The tellReviews take seconds. “Tests pass” has become the whole review.
Pay it downPut a real human gate where a mistake would be expensive, and treat it as a decision, not a rubber stamp.
Why this belongs in a guide about graphs. Martin Fowler's line between agentic engineering and vibe coding is that the human stays responsible for understanding the system. Graph structure will not pay these debts for you. It does give you named places to pay them: contracts, shared state, and gates.

Part 2 · The graph

A graph has four parts: nodes, edges, state, contracts.

V

Nodes do the work

A plain function, one model call, a tool, a human, or a whole agent running its own loop. Each node has one job.

E

Edges decide what runs next

Fixed handoffs, conditional branches, fan-out and fan-in, retry cycles. This is where you draw the line between code that must be deterministic and judgement you leave to the model.

G = (V, E, S, C)
agent (loop inside)plain codeverifierhuman gateretry edge
S

State is explicit

A typed, versioned record that nodes read from and write to. It replaces “whatever is in the chat history” and can be checkpointed, replayed and rolled back.

C

Contracts keep it honest

Input and output schemas, tool permissions, token and money budgets, retry limits, and what counts as done.

The practical definition (LangGraph): nodes do work, edges determine what runs next, state moves through the graph. Think of it as a state machine in which some of the states happen to be very capable agents.

Part 2 · The graph

Loops and graphs are zoom levels, not rivals.

“Loops are dead” is wrong. Graphs do not eliminate loops. They contain them.

Autonomy inside nodes, rules between them

In an open while-loop the model improvises its own control flow. In a graph the model is free inside each node, and you define how work moves from node to node.

Cycles are a feature

A data pipeline is a DAG: a step running twice is a bug. Agent graphs are cyclic on purpose. Retry, refine, ask, wait for approval. The cycles are just bounded.

What is actually new

A node can now be an entire agent that works through hundreds of tool calls and hands back a typed result. LangChain calls this the real reason the new term is justified.

Part 3 · Build one

Six patterns cover most of what you will build.

Five come from Anthropic's Building Effective Agents. The sixth is the one that keeps you out of trouble.

1

Prompt chain

A fixed sequence. Each step works on the structured output of the last, with a programmatic check in between.

Use when the steps are known and always the same.

2

Router

A classifier (code or a small model) inspects the input and sends it to a specialist path or a cheaper model tier.

Use when inputs fall into distinct kinds.

3

Parallelize

Fan out, then merge. Either split into independent sections, or run the same check several times and vote.

Use when subtasks do not need each other's output.

4

Orchestrator and workers

A lead agent breaks the task down at runtime, spawns as many workers as it needs, then synthesizes.

Use when you cannot predict the subtasks in advance.

5

Evaluator and optimizer

A generator paired with an independent verifier that has real authority to reject and send work back.

Use when quality must not be self-certified.

6

Gate before side effects

A deterministic check or human approval sits between a model's proposal and anything irreversible.

Use when a mistake would be costly or hard to undo.

Planner, worker, parallel reviewers, synthesizer, pass/fail gate. Five stages is the recommended ceiling for a first graph.

Part 3 · Build one

Stop using the chat log as your database.

Loop habit

State is the transcript

Plans, drafts, errors and decisions all pile into one history that every call re-reads.

Graph habit

State is a typed record

# each key has an owner and a merge rule
State
  task        str
  plan        Plan              planner writes
  patch       PatchCandidate    worker writes
  findings    list[Finding]     reducer: append
  tests       TestReport
  budget      tokens, retries   first-class
  approval    pending | granted

Nodes read what they need and write structured updates. Parallel writers merge through a reducer instead of overwriting each other.

Under the hood

Steps with a barrier

  1. Plan. Pick the nodes whose inputs changed.
  2. Execute. Run them in parallel, each reading the same frozen snapshot.
  3. Update. Commit all writes together, then checkpoint.

This is how LangGraph's Pregel runtime avoids agents corrupting shared memory mid-step.

What a checkpoint after every step buys you

Crash and resume

A shutdown stops the graph cleanly at a step boundary. A fresh instance picks up from the saved state.

Pause for a human

The run saves itself and releases compute. A person inspects, edits state if needed, and resumes.

Time travel

Open any earlier checkpoint, change a parameter or prompt, and fork a new branch without re-running upstream.

Retry only what broke

Keep validated upstream work. Roll back or re-execute just the corrupted part.

Sixteen agents, one bottleneck.

The most useful lesson about multi-agent systems comes from a stress test that hit a limit.

Parallelism works

Many independent failing tests

Each agent takes a different bug. Work divides cleanly, and progress scales with the number of agents.

Parallelism stalls

Everyone hits the same wall

All sixteen agents collide on one problem, repeat each other's work, and overwrite each other's fixes.

The experiment. In February 2026, Nicholas Carlini ran sixteen parallel Claude instances through almost 2,000 sessions to build a C compiler. Parallelism helped until the remaining work stopped being separable. The fix was not more agents. It was restructuring the test setup so the work split into independent pieces again.

A good graph does not just add nodes. It creates useful independence between them.Agent count is not the resource. Decomposable work is.

Part 4 · Reality check

Graphs fail in their own ways.

A graph is a control surface, not a safety proof. It can contain a failure, and it can also amplify one.

New ways to fail
  • Poisoned upstreamOne hallucinating or compromised node feeds bad input to every branch below it.
  • Shared-state racesTwo branches update the same key. Lost updates, stale reads, duplicate side effects.
  • Wrong routingA faulty router sends work to the wrong specialist, or the wrong permission level, every time.
  • Fan-out billsParallel branches multiply model calls. A harmful action also runs faster in parallel.
  • Bigger attack surfaceMore agents with more tools means more places for prompt injection to land.
  • An org chart of weak employeesDrawing a big graph before one capable agent has solved the task just multiplies surfaces and cost.
What to build in
  • Gate before anything irreversibleSchema checks, policy, spending limits, or a human between proposal and action.
  • Least privilege per nodeEach role gets only its own tools. Keep trusted and untrusted state apart.
  • Budgets and retry ceilingsEnforced by the runtime, not requested in a prompt.
  • CheckpointsContain a failure to one node. Resume instead of restarting.
  • Verifiers that are actually differentFive copies of the same model voting can be weaker than one deterministic check, one differently prompted critic and one external test.
  • Sparse wiringConnect only the nodes that need to talk. Start with 3 to 5 nodes.
Graphs are not safer by default. They give you more places to put safety, and more places to audit it.

Part 4 · Reality check

When loops multiply, someone has to govern them.

Ideas from control theory, via Carlos E. Perez and Eigent. Useful the moment you run more than one automated loop.

Four ways uncoordinated loops go wrong
  • Goodhart's collapseA loop sees only its one metric and learns to game it. More downloads through clickbait titles that burn audience trust.
  • Upward blindnessA feedback loop cannot step back and ask whether its target is still the right target.
  • Loops fighting loopsOne optimizes speed, its sibling optimizes thoroughness. A heater and an air conditioner in the same room, both dashboards green.
  • Nobody watching the watcherThe eval suite drifts away from real traffic while its scores keep climbing.
Four rules to wire into the graph
  • 1
    Metrics never travel alone.Pair every speed or volume metric with a quality or safety metric tied to something the model cannot game: real retention, real revenue, the compiler.
  • 2
    Every target has an owner.A human or higher-level loop sits upstream with the authority to audit, veto or roll back.
  • 3
    Separate the speeds.Real-time execution, daily prompt tuning, weekly operations, quarterly strategy. Fast loops escalate to slow ones. They do not override them.
  • 4
    Freeze the guardrails.Certain verification gates and approval rules are fixed, so a self-improving loop cannot optimize them away.
Two graphs, really. The work graph produces artifacts: code, reports, fixes. The improvement graph is the network of feedback loops that watch traces and adjust prompts, policies and other loops. The second one needs engineering too.

Test the wiring, not just the answer.

For coding agents this is unusually tractable: patches can be compiled, type-checked, linted, scanned and run against tests.

A testing ladder for graphs
Node testsDoes each function, tool adapter and agent honour its contract?
Edge and routing testsGiven this state, which transitions are possible?
Invariant testsCan a forbidden state or action ever be reached?
Subgraph testsDoes a whole capability, such as code review, hold up?
End-state testsWhat actually changed in the outside world?
Trajectory evalsEfficiency, tool choice, policy adherence, odd behaviour.
Repeated trialsSame input, many runs. Paths differ, so run it more than once.

Many different paths can reach the same good outcome. Judge the final state and the safety constraints. Use traces to diagnose, not to demand one canonical path.

Review questions that prompts never raised
  • Can an unverified value reach the payment node?
  • What happens if worker C times out?
  • Can these two branches write the same state?
  • Which graph version produced this side effect?

Part 5 · Your move

Loop or graph? Decide row by row.

Mostly left column: keep your loop. Several rows on the right: you have outgrown it.

Stay with a loop when…Move to a graph when…
OwnershipOne agent with one prompt and toolset can own the task end to end.The work needs different specialties, model tiers or separate permissions.
VerificationFewer than three checks. One test or rubric validates the result.Three or more independent checks, plus conditional routing.
ConcurrencySteps are strictly sequential and share the same tight context.Subtasks can run at the same time and be merged.
Pass rateBelow 50% per cycle. Fail fast, retry cheaply.At or above 50%. Fan-out cuts waiting by a third to 90%.
RecoveryShort runs that are cheap to replay from scratch.Long runs that need checkpoints, partial rollback, pause and resume.
Human oversightA person reviews the output afterwards, or chats along.High-stakes actions need approval before they execute.
Graphs are not the default. Choosing a single well-scoped loop early on is a deliberate advantage, not a shortcut. Anthropic's advice still stands: start with the simplest thing that works, and add complexity only when it earns its cost.
And it can go the other way. LangChain's own deep-research system moved away from a predefined graph and back toward an agentic core loop, because the best order of discovery could not be predicted ahead of time.

Part 5 · Your move

Before you automate anything, run the graph by hand.

A thirty-minute experiment with nothing but chat windows. It tells you whether a graph would help at all.

1

Name the output

Write the final deliverable in one concrete sentence. “A verified pull request.” “A one-page recommendation on whether this idea is worth testing.”

2

List the jobs

Write down the five to seven distinct jobs a competent human specialist would do to produce it.

3

Map real dependencies

Which jobs truly need another job's output? Ignore the order you happened to write them in.

4

Mark the gates

Wherever an error would have a large blast radius, insert a mandatory human checkpoint.

5

Play every node yourself

Open a fresh chat for each node. Pass only the output artifact from one chat into the next. No shared history.

The test
Automate the topology only if the isolated, node-by-node version clearly produces better output than one continuous chat session. If it does not, you have just learned that cheaply.
Why this works. Separate chats give each role its own context, exactly as separate nodes would. You experience the handoffs, discover which artifacts each step really needs, and find the gates, all before writing a line of orchestration code.

Part 5 · Your move

Five stages from a loop to a graph.

For when hand-testing and production traces agree that one loop is hiding structure.

Stage 1

Audit

Map every loop you run. Record steps per run, where retries cluster, wall-clock time, and token cost per successful task.

Start from data you already have: traces.
Stage 2

Identify

In those traces, find actions that do not depend on each other, and every place where the agent reviews its own work.

Security, logic and style checks. Docs, code and tickets. Unit, integration and end-to-end tests.
Stage 3

Design

Sketch the topology with a hard ceiling of 3 to 5 nodes. Write the six contracts for each one.

Planner → Worker → Parallel reviewers → Synthesizer → Pass/fail gate
Stage 4

Implement

Use a framework or plain async primitives. Keep measuring time saved against tokens spent, and watch the 50% pass-rate line.

asyncio.gather() is a perfectly good first runtime.
Stage 5

Type and govern

Give edges explicit meaning, make human approvals resumable steps, and anchor feedback loops to metrics that cannot be gamed.

depends_on · supersedes · decided_by · caused
Go in this order. The first two stages are observation only. Most of the value comes from stage 2: discovering which parts of your existing loop were secretly parallel, and where generation and verification were tangled together. Sometimes the answer is two changes to your loop, not a new architecture.

Part 5 · Your move

The tooling map, briefly.

Two schools: a central state machine with synchronized steps, or loosely coupled steps reacting to events.

Agent state machine

LangGraph

Typed state channels with reducers, cyclic retries, checkpoints after every step, time travel, human-in-the-loop pauses.

Event-driven steps

LlamaIndex Workflows

Decorate functions as steps that react to typed events. No global barrier, so fast branches do not wait for slow ones.

Graph-native runtime

Google ADK 2.0

Agents, tools and functions are all nodes. Graph, dynamic and collaborative workflows are core primitives.

Orchestration and tracing

OpenAI Agents SDK

Single and multi-agent orchestration with built-in tools and integrated tracing.

Durable execution

Temporal

Wraps node runs as activities: event-sourced history, timeouts, automatic retries across infrastructure crashes.

Data and lineage

Prefect / Dagster

Orchestrates the surrounding data assets so that agent runs stay reproducible and comparable.

Protocols are edges too. MCP connects an agent to tools and data. A2A connects one agent to another, including graphs owned by other teams.
A common production stack: LangGraph for the agent state machine, Temporal around each node for durability, Kafka for events between services.
You may not need any of it yet. Subagents, worktrees, a test gate and a tracker file already form a small graph. Structure first, framework second.

A ten-agent graph that beats one agent also used ten times the compute. Researchers are calling for equal-compute comparisons.

How much of the graph should be fixed?

Too rigid and capable models cannot find better strategies. The likely answer: fixed safety boundaries around model-chosen paths.

?

Who designs the graph?

Today, mostly you. Systems that compile a goal, policies and budget into a graph, then tune it from traces, are an open research area.

?

What does “verified” mean?

A schema can say a node returns evidence. It cannot say what counts as enough, or whether two agents agree on the word.

?

Are your verifiers independent?

Agents built on the same model and prompts share failure modes. Nobody yet knows how to measure that well.

?

Will the name last?

It may dissolve into older terms: workflows, state machines, distributed systems. The underlying need for explicit control will not.

The honest summary. Feng et al. present graph engineering as an emerging paradigm, not a settled discipline, and say the evidence does not yet show it improves performance everywhere. LangChain calls the term a buzzword for a real, long-standing engineering problem. Both can be true.

The one-page cheat sheet

Ten rules to keep next to your terminal.

  1. 01Start with one good loop. Graduate only when traces say so.
  2. 02Draw the graph before you code it. Run it by hand before you automate it.
  3. 03Keep autonomy inside nodes and rules between them.
  4. 04Never let a model grade its own work. Verify in a separate context.
  5. 05First graph: 3 to 5 nodes. Six contracts per node.
  6. 06Put state in a typed record with checkpoints, not in the transcript.
  7. 07Fan out only when work is truly independent and passes more than half the time.
  8. 08Make budgets part of the state: agents, calls, tokens, retries, money.
  9. 09Put a deterministic or human gate before anything irreversible.
  10. 10Add independence, not nodes.
The graph decides where autonomy helps, where plain code should take over, where work can fan out, where evidence must come back together, where state must persist, and where a person must say yes. Agentic nodes inside engineered topology.
